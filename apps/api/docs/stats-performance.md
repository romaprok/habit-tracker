# Запити статистики: EXPLAIN ANALYZE (BE-38)

Як відтворити:

```bash
npm run db:seed:perf -w apps/api   # ~100 тис. відміток: 400 користувачів × 3 звички × рік
npm run db:explain -w apps/api     # плани «до» і «після» для трьох запитів
```

«До» — це ті самі запити, але індекси видалені всередині транзакції, яку потім відкочуємо. DDL у PostgreSQL транзакційний, тож база після скрипта не змінюється. SQL береться з `src/modules/stats/stats.queries.ts`, тобто вимірюємо саме те, що виконує API.

Дані: 101 293 рядки в `habit_checks`, PostgreSQL 18, локальний Docker. Час — `Execution Time` з одного прогону, тож це порядок величин, а не бенчмарк.

## Які індекси працюють

Нових індексів не знадобилося: усе обслуговують ті, що з'явилися разом зі схемою.

- **`habit_checks_habit_id_date_unique` (habit_id, date)** — обмеження «одна відмітка на день» з `BE-12`. Унікальне обмеження в PostgreSQL — це B-tree індекс, а його перша колонка `habit_id` якраз та, за якою фільтрують усі три запити. Друга колонка `date` дає діапазон (`date <= today`) і готовий порядок для `row_number() over (order by date)`. Для стріків план навіть `Index Only Scan`: обидві потрібні колонки є в самому індексі, таблицю читати не треба (`Heap Fetches: 0` після `VACUUM`).
- **`habits_user_id_index`** з `BE-05` — знайти 3 звички користувача серед 1 204, а не перебирати всі (`Rows Removed by Filter: 1201` у плані «до»).

Окремий індекс на `habit_checks(date)` нічого б не дав: жоден запит не фільтрує за датою без `habit_id`.

## Що виправили завдяки EXPLAIN

Перший прогін показав у запиті відсотка виконання `SubPlan` з `loops=365` і `loops=30`, а час без індексів — **1 415 мс**. Причина: PostgreSQL вбудовує (inline) CTE `habit` у основний запит, і вираз `least(..., (select min(date) ...))` опинився в умові join. Тому підзапит виконувався заново для кожного рядка, з яким порівнювали.

Виправлення — `with habit as materialized (...)`: CTE рахується один раз, і далі план читає готовий рядок (`CTE Scan on habit ... loops=1`). Результат: без індексів 1 415 → ~20 мс, з індексами 0.49 → 0.14 мс. Індекс приховував проблему: кожен зайвий підзапит коштував мікросекунди. Без нього кожен такий підзапит ставав повним скануванням таблиці.

Перший замір робили на трохи інших даних (до виправлення сіду, див. нижче), але кількість рядків була та сама, тож порядок величин порівнянний.

## Попутно: баг у сіді

У першій версії `seed-perf.ts` умова `random() < 0.23` стояла в `WHERE` над `habits × generate_series`. Планувальник обчислив її один раз на звичку, а не на день, тож кожна звичка виявилася або відміченою щодня, або порожньою. Знайшли за підрахунком «відміток на звичку». Тепер `random()` рахується в матеріалізованому CTE поруч із днем.
