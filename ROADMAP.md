# Habit Tracker — роадмап

Пет-проєкт для практики **React, TypeScript, Node.js, Express і PostgreSQL**. Тут зафіксовано, з яким стеком стартуємо, у якому порядку рухаємось і що додаємо пізніше.

Оновлено: 2026-10-06 · Поточна фаза: **0 — підготовка репозиторію** · Задачі й прогрес — у [SPRINTS.md](SPRINTS.md)

## Як ми рухаємось

1. **Спочатку руками, потім інструмент.** Express до Nest, `useEffect` + `fetch` до TanStack Query, контрольовані форми до React Hook Form. Інструмент додаємо тоді, коли вже відчули проблему, яку він розв'язує.
2. **Вертикальні кроки.** Кожен спринт закінчується робочою функцією від бази до UI, а не «половиною бекенду». Тому фази 1 і 2 йдуть паралельно.
3. **Один контракт.** Zod-схеми й типи запитів і відповідей живуть у `packages/shared`. Їх використовують і `api`, і `web`.
4. **Критерій «готово».** У кожної фази є перевірюваний результат. Далі не йдемо, поки він не виконаний.
5. **Два документи без дублювання.** Тут — стек, фази, можливі розширення й журнал рішень. Конкретні задачі, їхній порядок і прогрес — у [SPRINTS.md](SPRINTS.md).

## Модель даних (MVP)

- **users**: `id`, `email` (unique), `password_hash` (nullable: у тих, хто входить лише через GitHub, пароля немає), `timezone`, `created_at`
- **habits**: `id`, `user_id` → users, `name`, `description`, `color`, `archived_at`, `created_at`
- **habit_checks**: `id`, `habit_id` → habits, `date`, `created_at`, unique `(habit_id, date)`
- **refresh_tokens**: `id`, `user_id` → users, `token_hash`, `expires_at`, `created_at`
- **oauth_accounts**: `id`, `user_id` → users, `provider`, `provider_user_id`, `created_at`, unique `(provider, provider_user_id)`

Таблиці з'являються поступово, через міграції: `users` і `habits` у фазі 1, `habit_checks` і `timezone` у фазі 3, `password_hash`, `refresh_tokens` і `oauth_accounts` у фазі 4.

Відмітка зберігається як `DATE` у часовому поясі користувача, а не як timestamp. Інакше відмітка о 23:30 за Києвом може «переїхати» на наступний день.

## Фази

### Фаза 0 — Підготовка репозиторію

- `git init`, `.gitignore`, перший коміт
- npm workspaces: `apps/web`, `apps/api`, `packages/shared`
- Перенести `frontend/` → `apps/web`, прибрати залишки шаблону (`App.css`, зайвий `<link>` на `index.css` в `index.html`, назва `front`)
- Оновити Vite до 8
- `docker-compose.yml` з PostgreSQL, `.env.example`
- Каркас Express: `GET /api/health` перевіряє з'єднання з БД
- Проксі у Vite: `/api/*` → Express
- Кореневі скрипти: `dev` (web + api разом), `lint`, `typecheck`
- Оновити README: PostgreSQL замість MongoDB, правильні шляхи

**Готово, коли:** `docker compose up -d && npm run dev` піднімає все, а сторінка в браузері показує статус з `/api/health`.

### Фаза 1 — Backend: Express + PostgreSQL

Практикуємо: роутинг, middleware, обробку помилок, розділення на шари, основи SQL, міграції.

- Шари: `routes → controllers → services → repositories`
- Конфіг з env, перевірений Zod: застосунок не стартує з битим `.env`
- Централізований обробник помилок, 404, логування (pino)
- Drizzle: схема `users` і `habits`, міграції, seed з demo-користувачем (поки всі звички належать йому)
- CRUD звичок: `GET/POST /api/habits`, `GET/PATCH/DELETE /api/habits/:id`
- Валідація тіла й параметрів запиту Zod-схемами з `packages/shared`
- Тести API: Vitest + Supertest на окремій тестовій БД

**Готово, коли:** весь CRUD працює через HTTP-клієнт (`.http`-файли або Bruno) і покритий тестами.

### Фаза 2 — Frontend: React

Практикуємо: компоненти, стан, ефекти, роутинг, типізацію API.

- React Router: сторінки «Звички», «Нова звичка», «Редагування звички»
- Типізований API-клієнт на `fetch` з типами з `packages/shared`
- Завантаження даних вручну: `useEffect` і стани loading / error / empty
- Форма створення й редагування: контрольовані компоненти, валідація тією самою Zod-схемою, що й на бекенді
- Перехід на TanStack Query: кеш, інвалідація після мутацій. Порівняти з ручним варіантом
- Адаптивна верстка на Tailwind, мобільна версія — основна

**Готово, коли:** звичку можна створити, змінити й видалити з браузера, а UI коректно показує завантаження й помилки.

### Фаза 3 — Відмітки

Практикуємо: зв'язки між таблицями, унікальні обмеження, роботу з датами, optimistic updates.

- Таблиця `habit_checks`; відмітити й зняти відмітку за день
- Часовий пояс користувача: «сьогодні» рахується в його поясі
- Екран «Сьогодні»: чекліст звичок з optimistic update
- Сітка останніх 7 днів для кожної звички

**Готово, коли:** звички можна відмічати щодня, а відмітка після 23:00 зберігається на правильну дату.

### Фаза 4 — Авторизація: JWT і OAuth

Практикуємо: хешування паролів, JWT, cookies, middleware авторизації, протокол OAuth 2.0, захищені маршрути.

OAuth і JWT розв'язують різні задачі. OAuth (вхід через GitHub) відповідає, *хто* користувач. JWT — як API *впізнає* його в наступних запитах. Обидва способи входу закінчуються однаково: Express видає наш JWT.

#### 4а — Email + пароль і JWT

- Реєстрація, вхід, вихід; пароль хешується argon2
- Короткий access-токен (JWT, ~15 хв) і refresh-токен (~7 днів), обидва в httpOnly cookies
- Refresh-токени зберігаються в БД як хеш і ротуються при кожному оновленні; вихід їх відкликає
- Middleware `requireAuth`; усі запити до звичок і відміток обмежені `user_id` поточного користувача
- Захист: helmet, rate limit на вхід, однакова відповідь на «немає такого email» і «невірний пароль»
- CSRF: cookies з `SameSite=Lax` і перевірка заголовка `Origin` для запитів, що змінюють дані
- Фронт: сторінки входу й реєстрації, захищені маршрути, поточний користувач, тихе оновлення токена при 401
- Demo-користувач лишається тільки в seed для розробки

**Готово, коли:** тест доводить, що користувач A не може прочитати, змінити чи видалити звичку користувача B (отримує 404), а після виходу старий refresh-токен більше не працює.

#### 4б — Вхід через GitHub (OAuth 2.0)

- OAuth-застосунок у GitHub; `GITHUB_CLIENT_ID` і `GITHUB_CLIENT_SECRET` в `.env`
- Authorization Code flow вручну, без бібліотек: редірект на GitHub зі `state`, callback, обмін `code` на токен, запит профілю
- Токен GitHub використовуємо один раз, щоб отримати профіль, і не зберігаємо
- Таблиця `oauth_accounts`: знайти або створити користувача
- Прив'язка до наявного акаунта за email — лише якщо GitHub позначив цей email як підтверджений. Інакше хтось може захопити чужий акаунт
- Після входу видаємо ті самі токени, що й у 4а
- Фронт: кнопка «Увійти через GitHub»

**Готово, коли:** в один акаунт можна увійти і паролем, і через GitHub, а `requireAuth` нічого не знає про спосіб входу.

### Фаза 5 — Статистика і глибше в PostgreSQL

Практикуємо: віконні функції, `generate_series`, індекси, аналіз запитів.

- Поточний і найдовший стрік одним SQL-запитом (віконні функції, задача gaps-and-islands)
- Річна теплокарта відміток (`generate_series`)
- Відсоток виконання за тиждень і місяць
- Індекси і `EXPLAIN ANALYZE` для запитів статистики
- Тести крайніх випадків стріків: пропуски, «сьогодні ще не відмічено», зміна часового поясу
- Фронт: сторінка статистики звички з теплокартою

**Готово, коли:** стріки й теплокарта рахуються на боці БД, а крайні випадки покриті тестами.

### Фаза 6 — Якість і деплой

- Тести фронту: Vitest + React Testing Library для ключових компонентів
- Один e2e-сценарій на Playwright: реєстрація → створення звички → відмітка
- GitHub Actions: lint, typecheck, тести (PostgreSQL як service-контейнер)
- Dockerfile для API
- Деплой: статика фронту, API і керована PostgreSQL. Конкретний хостинг обираємо на цьому етапі

**Готово, коли:** пуш у `main` проганяє CI, а застосунок доступний за публічним URL.

### Фаза 7 — NestJS

Практикуємо: модулі, dependency injection, декоратори, guards, pipes, interceptors.

- `apps/api-nest` з тим самим API-контрактом і схемами з `packages/shared`
- Модулі, контролери, провайдери; Drizzle як провайдер
- Авторизація через `@nestjs/passport` (стратегії JWT і GitHub). Порівняти з ручною реалізацією з фази 4
- Pipe для Zod-валідації, interceptor для логування
- Спільний набір API-тестів (через базовий URL) проходить для обох бекендів
- Короткі нотатки: що Nest спростив, а що ускладнив порівняно з Express

**Готово, коли:** `web` працює з `api-nest` без жодних змін у фронтенді.
